# From Zero PyTorch to Full-Stack Inference Engineer: A 24-Month Curriculum (Refined Edition)

## What changed in this refined edition

This is a precision pass over the original 10-phase plan. Every phase now specifies exact chapters, exact lecture numbers, exact papers, exact datasets, and exact library versions to use — not just topic names — plus a fully specified project per month with steps, required deliverables, and a numeric acceptance bar so "done" is never ambiguous. The phase structure, target end-state, and pacing philosophy are unchanged from the original plan; only the resolution has increased.

**Second change (this edition): RL now gets a dedicated three-month treatment instead of being folded into a two-month post-training grab-bag, and Phase H gets an explicit codebase deep-dive on vLLM's KV connector.** Both additions came from checking this plan against how RL-and-inference infrastructure engineers actually describe learning the field — starting with genuine RL fundamentals (a from-scratch PPO implementation, not just papers) before touching LLM-specific RLHF/DPO/GRPO, then a new month on how RL training loops actually run at production scale (verl/OpenRLHF-style architectures where an inference engine sits inside the training loop as the rollout generator). This pushes the realistic total from 24 to roughly **25 months** at the stated 15–20 hrs/week pace — treat that the same way the compressed/stretched variants below are treated: a known, deliberate trade-off for depth, not scope creep.

**Target end-state (unchanged):** by month 25 you can take a model architecture, understand or modify it, pretrain or post-train it (including RL-based post-training, and how RL training loops are actually wired to an inference engine in production), and serve it at production scale — reasoning correctly about GPU kernels, memory, batching, disaggregated serving, and quantization. **Pacing assumption:** 15–20 focused hours/week; compressed (25–30 hrs/week, ~17–19 months) and stretched (8–10 hrs/week, ~31–33 months) variants are still viable and noted per phase where they diverge meaningfully.

## Long-term risk-proofing: how this plan survives automation and tool churn

This edition is deliberately structured around four specific obsolescence risks rather than treating "stay current" as a vague footnote. Each risk gets a concrete curriculum-design response.

**Risk 1 — Tool churn (high probability, and normal).** Specific APIs (today's vLLM interfaces, today's Triton syntax, today's Dynamo config format) will be superseded within 2-3 years regardless of what you learn now. Response: every phase's core spine is chosen for the mental model it teaches, not the tool — PMPP and GPU MODE teach the memory-hierarchy/roofline model that outlives any specific compiler; the PagedAttention and RadixAttention papers are the assigned reading, with the vLLM/SGLang source code treated as one disposable implementation of that idea. When the tool changes, re-read the paper, not a new framework's quickstart.

**Risk 2 — Rote kernel-writing and autotuning getting AI-automated (moderate-to-high, already underway).** LLM-driven kernel generation already matches or beats hand-written kernels on many benchmark cases. Response: Phase F and Phase I now include an "audit the machine" exercise — you use an AI coding assistant to generate a kernel or quantization config, then use your PMPP/roofline fundamentals to verify, profile, and fix it. This makes you the person who supervises the automated tool rather than someone competing head-on with it at the one task where automation is winning fastest.

**Risk 3 — Commoditization from above: Dynamo/vLLM/SGLang absorbing the median serving case (moderate, historical precedent from MLOps tooling).** Response: the capstone (Phase J) is weighted toward the layer that doesn't commoditize — debugging why an automated system underperforms its theoretical roofline, and contributing to the engines themselves rather than only operating them as black boxes.

**Risk 4 — Hardware closing the memory-bandwidth gap and removing the problem (low probability in this window).** Compute throughput is still growing faster than memory bandwidth generation over generation, so the structural reason this discipline exists persists through your curriculum and beyond. No specific change needed; re-check this assumption at your Month 25 checkpoint.

## Phase A (Months 1–2): PyTorch, autograd, GPUs

### Month 1 — Python/NumPy → PyTorch bridge

**Materials, in this order:**
1. Re-derive your existing 1–2 layer plain-Python network's forward/backward pass in NumPy with explicit matrix calculus (no autograd), then port line-by-line to PyTorch and diff the gradients numerically (`torch.allclose` with `atol=1e-6`).
2. PyTorch official **"Learn the Basics"** series (tensors, autograd, `nn.Module`, optimization, saving/loading) — [pytorch.org/tutorials/beginner/basics](https://pytorch.org/tutorials/beginner/basics/intro.html) — and the **"Deep Learning with PyTorch: A 60 Minute Blitz"** — [pytorch.org/tutorials/beginner/blitz](https://pytorch.org/tutorials/beginner/blitz/). Do every code cell twice: once as written, once deliberately broken (wrong shape, missing `.detach()`, misused `requires_grad`) so you learn to read the actual PyTorch/CUDA stack trace, not just the tutorial's happy path.
3. `einops` documentation, specifically the **"Einops basics"** and **"Writing better code with einops"** notebooks — [einops.rocks](https://einops.rocks/1-einops-basics/) — rewrite three of your NumPy forward passes using `einops.rearrange`/`einsum` instead of `.view()`/`.permute()` chains.

**Project A1 — Autograd parity harness.** Build a small test harness (`pytest`) with 5 test cases (linear layer, 2-layer MLP, MLP + ReLU + softmax, MLP with a manual L2 regularizer, a toy RNN cell) where each case has a hand-derived NumPy gradient implementation and a PyTorch implementation, asserting `max_abs_diff < 1e-6` on gradients for random inputs across 20 seeds. **Acceptance bar:** all 5 cases pass on all 20 seeds; you can explain out loud, without notes, what `.backward()` does for each case.

### Month 2 — GPUs, mixed precision, profiling

**Materials, in this order:**
1. GPU MODE **Lecture 1: "Profiling and Integrating CUDA kernels in PyTorch"** (speaker Mark Saroufim) — introduces `torch.utils.cpp_extension.load_inline`, Triton, and Nsight Compute — [gpu-mode/lectures, lecture_001](https://github.com/gpu-mode/lectures).
2. GPU MODE **Lecture 4: "Intro to Compute and Memory Architecture"** (speaker Thomas Viehmann) — SMs, warps, HBM vs SRAM, why bandwidth (not FLOPs) is usually the bottleneck — [gpu-mode/lectures, lecture_004](https://github.com/gpu-mode/lectures).
3. PyTorch's **Automatic Mixed Precision (AMP) recipe** — [pytorch.org/tutorials/recipes/recipes/amp_recipe](https://pytorch.org/tutorials/recipes/recipes/amp_recipe.html) — and the **PyTorch Profiler tutorial** — [pytorch.org/tutorials/recipes/recipes/profiler_recipe](https://pytorch.org/tutorials/recipes/recipes/profiler_recipe.html).

**Project A2 — Profiled CIFAR-10 trainer.** Train a small CNN (e.g., a 4-conv-layer network, no pretrained weights) on CIFAR-10 to ≥70% test accuracy in ≤15 epochs, once in FP32 and once with `torch.autocast(dtype=torch.bfloat16)`, on a free Colab/Kaggle T4 or better. Capture a PyTorch Profiler trace (`torch.profiler.profile` with `record_shapes=True`) for both runs and produce a short written comparison of step time, GPU utilization %, and where time is spent (data loading vs forward vs backward). **Acceptance bar:** ≥70% test accuracy; a profiler trace you can open in Chrome tracing (`chrome://tracing`) and narrate; you can state the FP32-vs-bf16 speedup ratio you measured and explain why it isn't 2x even though bf16 halves memory.

## Phase D (Months 9–11): Distributed training systems

**Month 9 — parallelism fundamentals.** Hugging Face **Ultra-Scale Playbook**, read cover to cover with its interactive visualizations: data parallelism, ZeRO stages 1–3, tensor parallelism, pipeline parallelism, sequence/context parallelism, expert parallelism ([huggingface.co/spaces/nanotron/ultrascale-playbook](https://huggingface.co/spaces/nanotron/ultrascale-playbook)). In parallel, complete **CS336 Assignment 2: Systems** — profile and benchmark your Phase C model's layers, write a custom GPU kernel to optimize RMSNorm, and build a memory-efficient distributed version of your Assignment 1 model ([stanford-cs336/assignment2-systems](https://github.com/stanford-cs336)).

**Month 10 — real frameworks.** Install and run example multi-GPU training scripts with **DeepSpeed** (ZeRO optimizer-state/gradient/parameter sharding — [deepspeed.ai/training](https://www.deepspeed.ai/training/)) and **Megatron-LM** (tensor + pipeline parallelism for transformers — [github.com/NVIDIA/Megatron-LM](https://github.com/NVIDIA/Megatron-LM)). Deliberately misconfigure sharding (wrong ZeRO stage for your model size, mismatched tensor-parallel degree vs. GPU count) to observe and diagnose the resulting OOM/slowdown, since debugging these failure modes is the actual job.

**Month 11 — FSDP + NCCL communication reasoning.** PyTorch's **FSDP tutorial** — [pytorch.org/tutorials/intermediate/FSDP_tutorial](https://pytorch.org/tutorials/intermediate/FSDP_tutorial.html) — as the PyTorch-native ZeRO-3 equivalent. Study NCCL collective operations (all-reduce, all-gather, reduce-scatter) well enough to predict, for a given parallelism strategy, whether it is communication-bound or compute-bound at a given GPU count and interconnect (NVLink vs. InfiniBand vs. Ethernet).

**Project D1 — Multi-strategy scaling benchmark.** Take your Phase C 100M-parameter model and scale training across 4+ rented GPUs using at least two distinct strategies: (a) FSDP, and (b) a manual tensor-parallel implementation (splitting attention heads or MLP columns across devices by hand, not via a library). Produce a benchmark table of throughput (tokens/sec) and peak memory per GPU for both strategies at 2, 4, and 8 GPUs, with a written explanation of where each strategy's scaling breaks down and why. **Acceptance bar:** given a hypothetical model size and GPU count/interconnect you haven't tested, you can propose a parallelism strategy and give a first-order estimate of its communication overhead.

## Phase E (Months 12–14): RL fundamentals → LLM RLHF/DPO/GRPO → PEFT + RL infrastructure

Given zero prior RL background coming in, this phase is deliberately three months instead of the usual two, and deliberately sequenced so you build real RL mechanics on toy problems *before* touching LLM-specific RL — skipping straight to RLHF/DPO papers without this base is where most self-taught practitioners end up with vocabulary but no mental model.

**Month 12 — RL foundations, built from scratch, not just read.** Work through Hugging Face's **Deep RL Course** in this order: **Unit 1** (the MDP formalism — states, actions, rewards, policy \(\pi\), the discounted return \(G_t = \sum_k \gamma^k r_{t+k}\)), **Unit 2** (value functions and Q-learning, tabular case, on `FrozenLake`/`Taxi-v3`), **Unit 4** (policy gradients — derive and implement REINFORCE on `CartPole-v1` using raw PyTorch, no `stable-baselines3`), **Unit 6** (Actor-Critic/A2C — why a learned value function reduces the variance REINFORCE suffers from), and **Unit 8** (PPO — the clipped surrogate objective, Generalized Advantage Estimation) — [huggingface.co/learn/deep-rl-course/unit0](https://huggingface.co/learn/deep-rl-course/en/unit0/introduction). Skip the pure-game units (3, 5, 7). The critical difference from a lighter pass: for Units 4 and 8, do not stop at running the course's provided notebook — delete the solution cells and re-implement the training loop, the advantage calculation, and the clipped loss yourself against `gymnasium`'s `CartPole-v1`, checking your losses/rewards curve against the course's reference plot.

**Project E0 — PPO from scratch on CartPole (no RL library).** Using only PyTorch and `gymnasium` (no `stable-baselines3`, no `CleanRL` copy-paste — read CleanRL's PPO implementation *after* your own for comparison, not before: [github.com/vwxyzjn/cleanrl](https://github.com/vwxyzjn/cleanrl)), implement PPO end to end: a policy network, a separate value network, GAE for advantage estimation, and the clipped surrogate objective with an entropy bonus. **Acceptance bar:** your agent solves `CartPole-v1` (average reward ≥475 over 100 consecutive episodes); you can state, from memory, why PPO clips the probability ratio instead of just doing unconstrained policy-gradient ascent, and what specifically breaks if you remove the clip.

**Month 13 — From general RL to LLM-specific RL: RLHF, DPO, GRPO.** Read, in order: the original **InstructGPT/RLHF paper** framing (reward model trained on human preference pairs, then PPO against that reward model with a KL penalty to the reference policy — this is your Month 12 PPO, with the LLM as the policy and a learned reward model replacing the environment's reward signal), the **DPO paper** — *"Direct Preference Optimization: Your Language Model is Secretly a Reward Model"* ([arxiv.org/abs/2305.18290](https://arxiv.org/abs/2305.18290)), which shows the reward model and RL loop can be collapsed into a single closed-form loss — and the **DeepSeekMath paper**, which introduces **GRPO** ([arxiv.org/abs/2402.03300](https://arxiv.org/abs/2402.03300)), replacing PPO's learned value network with the average reward of a group of sampled completions for the same prompt. For each paper, explicitly map its objective back to the PPO/REINFORCE machinery you built in Month 12 — that mapping, not the paper's notation, is what you'll be asked to reproduce in an interview.

**Month 14 — PEFT (LoRA/QLoRA), then how RL training actually runs at scale.** First, **PEFT**: read the **LoRA paper** — *"LoRA: Low-Rank Adaptation of Large Language Models"* ([arxiv.org/abs/2106.09685](https://arxiv.org/abs/2106.09685)), reference implementation at [github.com/microsoft/LoRA](https://github.com/microsoft/LoRA) — and implement it yourself: insert trainable low-rank matrices \(A \in \mathbb{R}^{r \times d}\) and \(B \in \mathbb{R}^{d \times r}\) alongside a frozen weight \(W_0\), computing \(W_0 x + BAx\), before switching to the `peft` library for convenience on larger models. Then read the **QLoRA paper** ([arxiv.org/abs/2305.14314](https://arxiv.org/abs/2305.14314)) and implement LoRA on top of a 4-bit NF4-quantized frozen base model using `bitsandbytes`, measuring memory before/after. Second, and new in this edition: **RL infrastructure** — study **verl** ("HybridFlow"), the leading open RL post-training framework, at [github.com/verl-project/verl](https://github.com/verl-project/verl), specifically its architecture: **Megatron-LM/FSDP as the training backend** and **vLLM/SGLang as the rollout-generation backend**, running inside the same training loop. Read verl's architecture docs and, separately, skim **OpenRLHF**'s design ([github.com/OpenRLHF/OpenRLHF](https://github.com/OpenRLHF/OpenRLHF)) as a second reference implementation of the same pattern. The concept to nail down precisely: **rollout-training weight sync** — after each policy gradient step, the updated weights must reach the inference engine generating the *next* batch of rollouts before that batch starts, and production frameworks differ on whether training and rollout GPUs are **colocated** (same GPUs, in-memory weight hand-off, simpler but no parallelism between the two roles) or **disaggregated** (separate GPU pools, weights shipped over the network, higher throughput but a real synchronization/staleness problem to manage). This is precisely the "inference and training combined" infrastructure a senior RL-infra engineer would name as the frontier of this field.

**Project E1 — Full post-training pipeline on a small base model, run once by hand and once through verl.** Take a small open base model (e.g., a 0.5B–1.5B Qwen2.5 or SmolLM2 checkpoint, or your own Phase C 100M model if you want maximum from-scratch depth) through: SFT on an instruction dataset (e.g., a subset of `HuggingFaceH4/ultrachat_200k`) using LoRA → build a small preference dataset (200–500 pairs, can be model-generated + rule-scored) → DPO fine-tune → separately, implement a minimal GRPO loop with a simple verifiable reward (e.g., arithmetic correctness or exact-match on a small synthetic task) on the same base model, first by hand (your own rollout + reward + update loop), then re-run the same GRPO task using verl's example configs with vLLM as the rollout engine, and diff the two runs. Produce a before/after comparison: instruction-following quality (manual rubric-scored on 20 held-out prompts) and, for the GRPO run, task accuracy before vs. after RL. **Acceptance bar:** you can derive the DPO loss function on a whiteboard from the RLHF objective without looking at the paper; you can explain precisely why GRPO drops the separate value/critic network that PPO needs and what that costs and saves; you can point to the exact place in verl's config/logs where a rollout batch waits on updated weights from the training step, and explain whether your run was colocated or disaggregated.

## Phase F (Months 15–17): GPU programming & kernels

**Month 15 — CUDA fundamentals.** **Programming Massively Parallel Processors, 4th Edition** (Hwu, Kirk, El Hajj), **Chapters 1–6** — Ch.1 Introduction, Ch.2 Heterogeneous data parallel computing, Ch.3 Multidimensional grids and data, Ch.4 Compute architecture and scheduling, Ch.5 Memory architecture and data locality, Ch.6 Performance considerations. Pair each chapter with its matching GPU MODE lecture: **Lecture 2: "Recap Ch. 1-3 from the PMPP book"** (speaker Andreas Köpf), **Lecture 3: "Getting Started With CUDA for Python Programmers"** (speaker Jeremy Howard), and **Lecture 5: "Going Further with CUDA for Python Programmers"** (also Jeremy Howard) — all in [github.com/gpu-mode/lectures](https://github.com/gpu-mode/lectures). Write kernels for: vector add, naive matrix multiply, then a tiled matrix multiply using shared memory (this is the direct subject of PMPP Ch.5 and GPU MODE Lecture 5).

**Month 16 — Triton and fused attention.** Triton's own tutorial series, specifically **"Fused Softmax"** and **"Matrix Multiplication"** tutorials ([triton-lang.org/main/getting-started/tutorials](https://triton-lang.org/main/getting-started/tutorials/)), then work toward the **"Fused Attention" tutorial**, which is a simplified FlashAttention implementation. Read the **FlashAttention paper** alongside it — *"FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness"* ([arxiv.org/abs/2205.14135](https://arxiv.org/abs/2205.14135)) — to understand the tiling/recomputation trick (avoiding materializing the full \(N \times N\) attention matrix by keeping tiles in SRAM). Also cover PMPP **Chapter 10 (Reduction and minimizing divergence)** and **Chapter 7 (Convolution)** for the memory-coalescing and control-divergence vocabulary GPU MODE Lecture 8's "performance checklist" assumes.

**Month 17 — profiling and roofline analysis.** Nsight Systems and Nsight Compute (NVIDIA's official quick-start docs), the PyTorch Profiler's `torch.profiler` memory/kernel views, and roofline-model reasoning: for a given kernel, compute arithmetic intensity (FLOPs per byte moved) and compare against the GPU's FLOPs/bandwidth ratio to classify it as compute-bound or memory-bound. Optional depth: Stanford **CS149 (Parallel Computing)**, publicly available lecture notes and assignments, for the theory-heavy complement to GPU MODE's practitioner style ([cs149.stanford.edu](https://cs149.stanford.edu/)).

**Project F1 — Fused Triton attention kernel with roofline report.** Implement fused causal self-attention in Triton (following the tutorial's structure but writing the kernel yourself line-by-line, not copy-pasting), benchmark it against `torch.nn.functional.scaled_dot_product_attention` across sequence lengths {128, 512, 2048, 8192} and batch sizes {1, 8, 32}, and produce a roofline-style report classifying where each configuration sits (compute- vs. memory-bound) with your calculated arithmetic intensity numbers. **Acceptance bar:** your Triton kernel matches PyTorch's output within `1e-3` max abs error; you can correctly predict, before running it, whether a new sequence-length/batch-size combination will be compute- or memory-bound, and explain why LLM decode-time generation in particular is memory-bandwidth-bound.

**Project F2 — Audit the machine (risk-mitigation exercise).** Ask an AI coding assistant to generate a fused kernel for a different op (e.g., layernorm or a fused bias+GELU) without giving it your Triton reference implementation. Profile its output with Nsight Compute/PyTorch Profiler, deliberately try to find a case where it underperforms or is subtly wrong (wrong stride handling, missing masking, poor occupancy), and fix it by hand. Write a short note on what the model got right, what it missed, and why your PMPP/roofline background was what let you catch it. **Acceptance bar:** you find and fix at least one real correctness or performance issue in the AI-generated kernel using only your own profiling and reasoning — this is the specific skill (supervising automated kernel generation) that the obsolescence-risk analysis flagged as the durable half of the job.

## Phase G (Months 18–20): Inference engine internals

**Month 18 — batching and memory: vLLM and PagedAttention.** Read the **PagedAttention paper** — *"Efficient Memory Management for Large Language Model Serving with PagedAttention"* ([arxiv.org/pdf/2309.06180](https://arxiv.org/pdf/2309.06180)) — then, in the vLLM source ([github.com/vllm-project/vllm](https://github.com/vllm-project/vllm)), read the scheduler (`vllm/core/scheduler.py`) and the block manager (`vllm/core/block_manager.py`) to connect the paper's "page table for KV cache" abstraction to real code. Deploy vLLM locally serving a small open model (e.g., Qwen2.5-1.5B-Instruct) and step through a request with a debugger to watch block allocation happen. Cross-reference [docs.vllm.ai](https://docs.vllm.ai/en/latest/) for the current architecture docs, since the internal file layout does shift between releases.

**Month 19 — SGLang's RadixAttention and TensorRT-LLM's compiled approach.** Read the **SGLang paper** — *"SGLang: Efficient Execution of Structured Language Model Programs"* ([arxiv.org/pdf/2312.07104](https://arxiv.org/pdf/2312.07104)) — focusing on the RadixAttention section, which stores KV cache in a radix tree keyed by token prefix with an LRU eviction policy, enabling automatic cross-request cache sharing. Deploy SGLang serving the same model as Month 18 and test prefix-sharing behavior directly: send 20 requests sharing a long common prefix (e.g., a fixed system prompt) and 20 requests with no shared prefix, and observe the throughput difference. Separately, skim **TensorRT-LLM's** docs ([nvidia.github.io/TensorRT-LLM](https://nvidia.github.io/TensorRT-LLM/)) to understand its ahead-of-time compilation/kernel-fusion approach as the throughput-optimized, less-flexible alternative to vLLM/SGLang's dynamic scheduling.

**Month 20 — speculative decoding, hands-on.** Read the **EAGLE paper** — *"EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty"* ([arxiv.org/abs/2401.15077](https://arxiv.org/abs/2401.15077)) — which drafts using the target model's own hidden states rather than a separate draft model. Implement or run an existing minimal implementation such as **BaldEagle** ([github.com/NickL77/BaldEagle](https://github.com/NickL77/BaldEagle), reports a 3.17x speedup on Llama-3.1-8B) to see the mechanics end to end, then enable EAGLE-style speculative decoding in your own SGLang deployment and measure the speedup on two workload types: one where the draft model matches the target's domain well (e.g., code) and one where it doesn't (e.g., creative writing) — this directly tests the workload-sensitivity behavior of speculative decoding.

**Project G1 — Dual-engine deployment and load-test comparison.** Deploy the same open model on both vLLM and SGLang on the same hardware, build a load-testing script (e.g., using `vllm bench serve` or a custom `asyncio` client) that varies concurrency (1, 8, 32 concurrent requests) and prompt structure (unique prompts vs. shared-prefix prompts), and report time-to-first-token (TTFT), inter-token latency, and total throughput for both engines under both traffic patterns. **Acceptance bar:** your report shows a measurable throughput advantage for SGLang specifically on the shared-prefix workload (consistent with RadixAttention's design purpose) that is smaller or absent on the unique-prompt workload; you can whiteboard, from memory, how PagedAttention decides which KV blocks to allocate/evict for a new request.

## Phase H (Months 21–22): Advanced distributed serving

**Month 21 — disaggregated serving, and the KV connector that makes it work.** Read the **DistServe paper** — *"DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving"* (search for the current arXiv listing, as this defines the "goodput" metric — throughput meeting a latency SLO — that the field now uses to justify PD disaggregation) — then study **NVIDIA Dynamo**, the production framework for this pattern: disaggregated serving, cross-worker KV cache transfer, and fleet-aware request routing ([developer.nvidia.com/dynamo](https://developer.nvidia.com/dynamo), [github.com/ai-dynamo/dynamo](https://github.com/ai-dynamo)). Work through Dynamo's own quick-start deploying a disaggregated prefill/decode setup on 2 GPU pools. Then go one layer deeper than the paper, into the actual code that moves KV cache between a prefill and a decode instance: vLLM's **`KVConnectorBase_V1`** abstraction ([docs.vllm.ai/en/stable/api/vllm/distributed/kv_transfer/kv_connector/v1](https://docs.vllm.ai/en/stable/api/vllm/distributed/kv_transfer/kv_connector/v1/)) — the base class every disaggregation backend (NIXL, LMCache, etc.) implements to hand KV blocks from a producer (prefill) instance to a consumer (decode) instance. Don't try to read the whole vLLM codebase at once; point an AI assistant specifically at the `kv_connector` module and its concrete implementations, and study only that one component until you can explain its producer/consumer roles and metadata-binding methods without the assistant's help.

**Month 22 — multi-tier KV cache.** Study KV cache movement across memory tiers (GPU HBM → CPU RAM → remote/networked storage) for long-context workloads where cache reuse across requests becomes economically significant. Build a small multi-node (or multi-GPU-pool-on-one-instance) deployment separating prefill and decode workers with KV cache transfer between them, using Dynamo or a hand-rolled minimal version (a prefill server that computes KV cache and ships it over the network to a decode server) if Dynamo's setup is too heavyweight for your hardware budget.

**Project H0 — KV connector deep dive (codebase-first, no paper).** Using only the vLLM source and an AI assistant as a navigation tool (not as the one doing the understanding for you), trace one real disaggregated-serving request end to end through the `kv_connector` module: where the prefill instance's connector signals "KV ready," how the metadata identifying which blocks to transfer is built (`build_connector_meta`), and how the decode instance's connector consumes it. Separately, compare this to how **NVIDIA Dynamo** performs the equivalent transfer (via NIXL) and write a short note on the two designs' trade-offs. **Acceptance bar:** you can diagram the producer/consumer handoff for a single request from memory, and you can name at least one edge case (e.g., a request preempted mid-handoff) that the connector abstraction has to account for.

**Project H1 — Disaggregated vs. co-located serving benchmark.** Implement a disaggregated prefill/decode system (via Dynamo, or a simplified hand-built version using two vLLM/SGLang instances plus a KV-cache-transfer mechanism) and benchmark it against a standard co-located deployment under an agentic-style synthetic workload: long, mostly-shared prompt prefixes (simulate a fixed system prompt + tool definitions) with short, variable-length generations. Report goodput (requests/sec meeting a chosen latency SLO, e.g., TTFT < 200ms) for both architectures across at least 3 request-rate levels. **Acceptance bar:** your own numbers show at least one request-rate regime where disaggregation improves goodput and at least one (e.g., very low concurrency) where it doesn't — and you can explain why in terms of prefill being compute-bound/parallelizable and decode being memory-bandwidth-bound.

## Phase I (Months 23–24): Compression, quantization, and frontier serving techniques

**Month 23 — quantization, implemented not just called.** Read the **GPTQ paper** — *"GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers"* — and the **AWQ paper** — *"AWQ: Activation-aware Weight Quantization for LLM Compression and Acceleration"* — then quantize a model you've already served (from Phase G/H) using both **AutoGPTQ** ([github.com/AutoGPTQ/AutoGPTQ](https://github.com/autogptq/autogptq)) and **AutoAWQ** ([github.com/casper-hansen/AutoAWQ](https://github.com/casper-hansen/AutoAWQ)) at 4-bit with `group_size=128`. Also cover **SmoothQuant** (activation-to-weight quantization-difficulty migration) and **FP8** (the Hopper/Blackwell default) conceptually, since production stacks increasingly default to FP8 over INT4 for a smaller accuracy hit at similar throughput gains.

**Month 24 — MoE serving and DeepSeek's sparse-attention case study.** Study how Mixture-of-Experts changes serving: expert parallelism, load balancing across experts under real (non-uniform) routing, and the fact that only a small fraction of parameters activate per token. Then work through **DeepSeek-V3.2's** evolution from Multi-head Latent Attention (MLA) to DeepSeek Sparse Attention (DSA) as a live case study — read the technical report/paper for the architecture ([arxiv.org/pdf/2512.02556](https://arxiv.org/pdf/2512.02556)) and note that inference engines sometimes disable the sparse indexer at short context lengths because it's *less* efficient there — a concrete example of a researcher's optimization becoming an inference engineer's conditional judgment call, not a strict win.

**Project I1 — Quantization accuracy/latency/cost report.** Quantize a model you've previously served using both AutoGPTQ (4-bit) and AutoAWQ (4-bit), and evaluate each against the unquantized baseline on: (a) a real accuracy benchmark for your model's domain (e.g., a subset of MMLU or HellaSwag via `lm-evaluation-harness`, not a vibes check), (b) throughput (tokens/sec) at a fixed batch size, and (c) estimated cost-per-million-tokens given your GPU's hourly rental cost. **Acceptance bar:** your accuracy delta is quantified (e.g., "AWQ: -1.2 points on HellaSwag, GPTQ: -2.1 points") rather than described qualitatively; given an unfamiliar architecture announcement with a new efficiency trick, you can predict its likely serving-cost impact before reading any third-party analysis.

**Project I2 — Audit an autotuner (risk-mitigation exercise, continued from Phase F).** Run an automated quantization-config search (e.g., AutoAWQ's or AutoGPTQ's own calibration/search settings, or a compiler autotuner like `torch.compile`'s `max-autotune` mode) on your Phase I1 model, and compare its chosen configuration against one you pick by hand using your own understanding of activation outliers and group size. Note any case where the automated choice is measurably worse, and explain why using your Month 23 reading. **Acceptance bar:** you can articulate, with your own numbers, at least one gap between what the autotuner picked and what a first-principles choice would have picked — reinforcing that automation handles the median case well but the judgment layer still catches the tail cases.

## Phase J (Month 25): Capstone and job readiness

**The capstone.** One coherent end-to-end system: take an open base model, post-train it (SFT + DPO or GRPO, using LoRA) for a specific task of your choosing, quantize it (AWQ or FP8), and serve it through a self-deployed vLLM or SGLang instance with at least one advanced feature from Phases G–H (prefix caching, speculative decoding, or basic PD disaggregation). Ship a public write-up with your own benchmark numbers (latency, throughput, accuracy before/after each pipeline stage) — this project should be able to anchor an entire technical interview end to end.

**Open-source contribution.** Target **vLLM** ([github.com/vllm-project/vllm](https://github.com/vllm-project/vllm)) or **SGLang** ([github.com/sgl-project/sglang](https://github.com/sgl-project/sglang)) — both extremely active with clearly labeled "good first issue" tags. Start with a documentation fix or small bug fix to learn the contribution workflow, then look for open issues tagged around kernels, scheduling, or quantization support once you're oriented. A merged PR to a major inference engine is one of the strongest possible signals for this specific career path, and it is also the single most direct hedge against Risk 3 above (tooling commoditizing the median case) — contributors to the tool are rarely the ones the tool replaces.

**Deliberately weight your capstone toward debugging, not just assembling.** Given the automation risks this curriculum was designed against, treat "my pipeline runs end to end" as the floor, not the goal. The stronger version of this capstone includes at least one documented case where something in your stack (an automated batching decision, a quantization config, a scheduler choice) underperformed its theoretical roofline, and you diagnosed and fixed why — that diagnostic narrative is what separates "operated the tools" from "understood the tools" in an interview.

**Job-readiness checkpoint.** By month 25 you should be able to speak fluently, backed by your own projects rather than borrowed vocabulary, to postings like NVIDIA's LLM inference kernel-optimization roles and Together AI's ML Engineer – Inference / Forward Deployed Engineer (Inference & Post-Training) roles — GPU kernel-level optimization, distributed systems experience, and the judgment to connect model-level behavior to serving economics are the consistent, explicit asks across this role family.

## Staying current (this field moves in weeks, not years)

No 24-month curriculum can hard-code every future development — DeepSeek's sparse attention went from paper to day-0 support in both vLLM and SGLang within roughly 24 hours of release. Starting in Phase F onward, build these habits: follow vLLM and SGLang release notes and GitHub issues directly, skim new frontier lab technical reports (DeepSeek, Qwen, Llama, and the major US labs) for their "why we did this" sections rather than headline benchmarks, and for every new technique you encounter, ask "what does this do to memory, compute, and batching at serving time" — that question, repeated for two years, is what builds the judgment this field actually pays for.

**The quarterly fundamentals audit (the actual long-term-scaling mechanism).** Every 3 months from Phase B onward, spend one session re-deriving, from memory and with no notes, the handful of ideas with the longest half-life: causal multi-head self-attention, a KV cache, the DPO loss from the RLHF objective, what PagedAttention's block table is doing, and a roofline calculation for a kernel you haven't looked at recently. If any of these has gone rusty, that is a stronger signal to revisit than any new tool release — tools you can re-learn in a weekend when you need them; the mental models above are what let you re-learn a new tool in a weekend instead of a month. This single habit is the mechanism by which "learn good and scale long term" actually happens: it keeps the durable 20% of the curriculum sharp while the disposable 80% (specific APIs) is allowed to lapse and be rebuilt on demand.

## Adjusting the pace

If you can commit 25–30 hours/week, Phases B–D and G–I compress well since they're project-driven; a realistic compressed timeline is 17–19 months. If you can only commit 8–10 hours/week, extend Phases E, F, and G first, since RL foundations and GPU programming are where under-practicing shows up most in interviews; a realistic stretched timeline is 31–33 months. Do not compress the milestone projects themselves in either case — they are what makes each phase's knowledge durable rather than passively read. Phase E specifically should not be compressed below its new three-month allocation even under time pressure — a rushed RL foundation is exactly the "vocabulary but no mental model" gap this edition was expanded to close.
